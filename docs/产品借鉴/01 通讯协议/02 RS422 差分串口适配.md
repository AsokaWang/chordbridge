# RS422 差分串口适配借鉴

核查日期：2026-10-24。本文为 GitHub 与官方资料研究，不是代码实现或硬件实测。

.NET 是用户已确认的实现方向；下述具体库和设计仍是候选建议。Windows x64、Linux x64、Linux ARM64、Windows ARM64 必须逐项验证，不能由“.NET Standard”推导出驱动和全部功能已经兼容。

## 结论

不应寻找一个与 RS232 完全不同的“RS422 软件协议库”。操作系统通常向程序提供串口，软件可以共用串口传输层；电气接线、收发器模式、驱动和设备报文才是差异。RS422 的单驱动多接收器特征不等于可直接当成任意多主 RS485 总线。双向连接常使用独立发送、接收差分对，不能仅凭“四根线”判定协议。[TI 接口说明](https://www.ti.com/lit/an/slla070d/slla070d.pdf)

## 建议设计

- 连接类型显式标 RS422，并记录适配器型号、接线说明与驱动信息；不要假装设置一个软件枚举就能把普通 RS232 硬件改成 RS422。
- 共用 RS232 的分帧、脚本、原始报文、标签调用层，不复制业务实现。
- 请求响应式设备依然默认单事务占用连接；电气上可同时收发，不意味着设备允许多条查询并发。
- 对会主动上报的设备，模板需区分“主动帧”和“请求响应帧”，不能把任何接收数据都匹配到当前请求。
- 同周期组只影响何时触发操作，不改变设备接线或收发方向规则。

## 候选选择建议

优先与 RS232 统一评估 System.IO.Ports 和 RJCP。TouchSocket 的价值是复用分帧管道，而不是自动处理电气差异。不要单独引入一个仅凭名称带 RS422、维护和许可证不明的库。

## 未覆盖与平台风险

公开串口库没有替弦桥认证具体 USB 适配器。ARM64 驱动、Linux 设备权限、稳定端口命名和收发器配置仍需验证。厂商驱动控制 API 若仅支持 Windows，应隔离到平台适配层，不侵入标签核心。

## 后续验收证据

- 至少一台实际 RS422 设备，在目标系统与架构下验证双向收发、断线和恢复。
- 主动上报与查询响应交错时，标签结果不串单；不能匹配时明确报告未知帧。
- 不同模板实例共享规则但独立保存端口参数。
- 电气接线与终端匹配按设备、适配器手册确认；软件不自动替用户修改硬件设置。
