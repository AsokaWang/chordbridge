# 同周期定时组与合并调度的实现借鉴

核查日期：2026-10-24。本文是基于 GitHub 与官方资料的借鉴研究；“建议”不是已确认的详细设计，也不是已实现或实测结果。用户已选择 .NET 方向，具体版本与依赖尚未锁定。

## 结论

弦桥的 500 毫秒、2 秒组是设备通讯调度，不是普通后台业务作业。建议先采用 .NET 内存调度器＋按连接串行执行器；Quartz 可作为较复杂日历调度候选，Hangfire 不作为 500 毫秒轮询基础。

## 已核查候选

- [dotnet/runtime](https://github.com/dotnet/runtime)：MIT，main，2026-10-24 最近推送。官方 [PeriodicTimer 语义](https://learn.microsoft.com/en-us/dotnet/api/system.threading.periodictimer.waitfornexttickasync?view=net-10.0) 说明多个未消费 tick 会合并，且只允许一个等待消费者。它是构件，不是已实现的组调度器。
- [Quartz.NET](https://github.com/quartznet/quartznet)：Apache-2.0，2026-10-20 最近推送。SimpleTrigger 支持 TimeSpan 间隔与误触发处理；当前 main README 指向 .NET 10 的 4 系列，3.x 有独立维护分支。毫秒精度表示可表达间隔，不代表 Windows/Linux 能保证硬实时或设备能按时响应。[SimpleTrigger 文档](https://www.quartz-scheduler.net/documentation/quartz-3.x/tutorial/simpletriggers.html)
- [Hangfire](https://github.com/HangfireIO/Hangfire)：2026-10-21 最近推送，未归档；[许可](https://github.com/HangfireIO/Hangfire/blob/main/LICENSE.md) 提供 LGPL v3 或商业许可。官方 recurring job 按分钟检查，不能以它直接满足 500 毫秒组。[官方说明](https://docs.hangfire.io/en/latest/background-methods/performing-recurrent-tasks.html)

## 弦桥建议落地

组是统一的 period：标签调用设 500ms 时创建或复用 500ms 组，拖入也变为该周期；2s 另组。组成员引用标签及读取、写入、动作或组合调用，而非复制标签。

调度器只产生到期意图；连接执行器负责端口独占、事务顺序和容量。用单调时间计算到期时间，记录期望触发、实际开始、完成及跳过原因。超期时不堆积无限补跑；同一调用未完成时不能重叠启动。

仅对同一连接、同一查询语义、相同参数且同一到期窗口的读取合并。一次响应返回多个字段时共享结果批次。跨组缓存复用必须满足新鲜度和周期语义，不能把 2s 的旧读冒充本次 500ms 读；写入、去皮等有副作用动作不做“去重合并”。

## 缺口与风险

周期组跨设备的作用域、同一标签多组引用规则尚未确认。建议以调用为排程单位并显式检测冲突；不能宣称任何上游框架直接提供该产品交互。还需区分操作超期和页面刷新慢。

## 后续验证证据

拖入500ms组后实际采用500ms；改为2s正确迁移；一帧三标签只有一条读取请求；一次操作800ms不会堆积补跑；慢串口不阻塞其他连接；系统时钟校正不产生突发写入；记录延迟分布与最大队列长度，而不是只验证计时器能触发。
