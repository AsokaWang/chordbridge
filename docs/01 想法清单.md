# 弦桥 ChordBridge 想法清单

更新日期：2026-10-24  
状态：需求讨论已确认；功能尚未实现、未进行设备测试或验收。

本文合并最初构想与本次逐条讨论的结论，作为后续产品、技术和任务拆分的依据。本次仅建立想法清单，不代表其他方案文档已经完成，也不启动程序开发。

## 1 产品定位

弦桥是一个多协议通讯测试与控制工具。用户可以连接设备、测试收发、配置或浏览标签、执行读取与控制，再把调试成果保存为可复用的设备标签模板。

核心不是简单的串口报文收发，也不是建设完整 SCADA 或云平台。核心流程是：**连接设备 → 调通通讯 → 解析与建立标签 → 统一调用标签 → 按周期执行与观察反馈 → 保存模板复用。**

定时功能既支持读取，也支持明确配置的写入或动作调用，不只用于被动监视。

## 2 必须覆盖的通讯范围

- RS232、RS422、RS485。
- Socket 通讯。
- Modbus RTU、Modbus TCP。
- OPC UA、OPC DA。

串口接口、网络传输和应用协议属于不同层次，但上述范围均保留，不用“支持某个协议”替代其他要求。具体设备是否支持某项能力，以设备协议和实际测试为准。

连接参数应可配置、保存并用于重复测试。具有浏览能力的协议可浏览、选择已有点位或标签；不能浏览的设备按手册或已配置模板建立指令与标签。Modbus 有寄存器地址不等于能够自动发现地址的业务含义。

## 3 通讯测试与调试成果复用

- 支持单次读取、写入和指令测试，查看原始发送内容、响应内容、解析结果及错误。
- 自定义串口或 Socket 通讯可使用 ASCII、HEX 等适合设备的报文方式。
- 调试成功后，直接把请求、响应分帧、解析规则、脚本、标签和控制逻辑保存下来，不必到另一处重新录入。
- 新设备从测试开始，逐步把报文规范为设备标签；已有模板的设备直接带出已配置内容，再填入实际连接参数并测试。
- “自动带出”以已配置模板和协议提供的浏览能力为依据，不承诺软件凭空猜出未知设备指令或字段含义。

## 4 可视化配置与脚本同时支持

常见报文可以通过可视化完成配置；复杂情况允许使用脚本，两种方式可以配合使用。

发送端支持参数填充、指令生成、编码和校验处理；接收端支持响应边界与完整性判断、字段提取、数据类型转换、数值换算和校验。具体规则根据设备协议配置。

两种方式共用调试预览：
- 同时查看原始报文、解析字段、映射后的标签值及错误位置。
- 可保存真实响应样例，修改规则或脚本后重跑样例，检查是否影响原有解析。
- 解析失败时保留原始报文并明确报错，不能把失败伪装成数值 0，也不能把上一次结果当成本次新结果。

脚本语言、运行权限、隔离机制和编辑器选型留待技术方案确认，不因支持脚本而默认允许任意系统操作。

## 5 设备模板与设备实例分开

设备模板保存可复用的协议规则、指令、解析、脚本、标签定义及调用流程。设备实例保存自己的连接地址、通讯参数和必要的个体差异。

同型号设备可复用模板，而不相互覆盖实际连接配置。模板更新时先展示差异，再决定哪些设备采用更新，不默默修改所有正在使用的实例。

遇到新设备时仍可从通讯测试开始，最终形成同样的设备标签模板。模板的目的是沉淀调试成果，不是把设备差异隐藏起来。

## 6 以标签调用作为统一入口

**最终以“调用标签”使用设备能力，不以制作按钮为产品核心。**

标签保留独立定义。名称、别名可以自定义；稳定标识、来源地址或绑定关系不应因为改名而改变。

统一入口需要区分：
- **查看当前值**：返回最近一次结果及更新时间，不主动发送通讯请求。
- **执行读取**：调用标签绑定的读取逻辑，实际请求设备并更新结果。
- **写入数值**：把传入值交给标签绑定的写入逻辑，生成对应指令或协议写操作。
- **调用动作**：执行明确的控制动作，如去皮，而不是把它误当成普通数值读取。

数据标签与动作标签按类型区分；并非每个标签都支持所有操作。标签可绑定串口指令、自定义 Socket 报文、Modbus 点位、OPC 标签或组合流程。界面和脚本复用这套调用语义，用户不必每次重新拼报文。

例如：
- 读取“重量”标签，执行其绑定的查询、接收和解析。
- 向“目标转速”写入一个值，执行对应的参数化写入。
- 调用“去皮”动作标签，执行设备的去皮指令。

未来 API 可以考虑复用该入口，但 API 形式及交付范围尚未确定。

## 7 标签信息与运行结果

标签定义应表达：
- 稳定标识、名称、别名和用途。
- 数据或动作类型，数据类型、单位及适用的参数范围。
- 来源点位、地址、解析字段或绑定指令。
- 支持读取、写入还是动作调用，以及对应参数。

运行结果应能看到最新值、更新时间、通信或数据质量、错误状态，以及必要的反馈记录。历史值可以保留，但必须保留其原有时间，并标明过期、失败或未知，不能看起来像刚刚读取成功。

重量、单位、稳定状态可以来自同一条响应；“收到合法报文”与“称重已稳定”是不同信息，不能混为一个成功状态。

## 8 按执行周期自动组织定时组

**同一个定时组使用统一周期。不是仅用于分类的文件夹，也不允许组内各项保留不同周期。**

确认的交互方式：
1. 将某标签的读取或写入设为每 500 毫秒一次，自动创建或复用“500 毫秒定时组”。
2. 将其他标签拖入该组，它们也按 500 毫秒执行；加入时须明确调用的是读取、写入还是动作，写入还需明确值或参数。
3. 另一个标签设置为每 2 秒执行一次，自动创建或加入“2 秒定时组”。
4. 1 秒、2 秒、5 秒等不同周期分别组织，不能混在同一个组里使用不同周期。

标签定义仍独立存在；定时组引用标签及其调用方式，而不是复制标签定义。组中可以安排完整读取、写入、动作或已绑定的组合流程。

允许在不改变上述周期语义和调用结果的前提下合并重复读取。例如，一次查询返回重量、单位和状态，可用同一条响应更新多个标签，不应为每个字段重复发送同一查询。不得据此随意合并有副作用的写入或动作。

用户设定周期表示期望的触发周期，不等于设备必定能在该时间内完成。应显示实际执行时间、延迟或超期，避免宣称串口能提供无法保证的实时性。重复引用、跨组冲突和排程细节留待后续方案明确。

## 9 区分完整读取与先写后读

两类情况都要支持，不能仅根据“发送过字节”就认定为写标签。

### 9.1 发查询后接收响应

向称重设备发送查询指令，再接收并解析响应，是一次完整读取事务。发送查询本身不必建立第二个标签；一条响应可以更新一个或多个标签。

### 9.2 写参数后读回核对

真正修改设备参数，再读取反馈确认，是一个组合流程。写入目标和读回结果可以关联不同标签，也可以绑定到统一的标签调用入口。

组合流程支持顺序执行、等待响应、条件判断和失败停止，保留每一步记录。定时组触发的是整个流程，而不是互不关联地启动两个步骤。

同一串口上的完整事务或组合流程不能被其他普通任务交错插入，避免响应对应错误。若一轮执行超过设定周期，应报告超期，不重叠启动同一操作、不无限堆积补跑任务。

## 10 失败和执行结果要说清楚

- 区分“已发送”“收到响应”“读回符合预期”和“实际控制效果已确认”。收到响应不自动等于设备已经完成物理动作。
- 读取可按协议规则配置超时和有限重试，但不能把所有名为读取的操作都当作无副作用、可随意重试。
- 写入或控制超时不能盲目重发。支持且适合读回时先核对；仍无法确认则标记“结果未知”，由用户决定是否再次执行。
- 组合流程默认在失败处停止，保留已完成和未完成步骤，不伪装为整组成功。
- 保留原始报文、错误、时间与必要的关联信息，便于定位是通讯、解析还是控制反馈问题。

## 11 手动调试与定时任务协调

同一连接的手动调用与定时调用使用共同调度，提供两种方式：

1. **排队执行**：默认等待当前完整事务或组合流程结束，再执行手动请求。
2. **中断后执行**：用户明确选择时停止当前软件操作，再安排手动请求；必须处理或隔离迟到响应，不能把旧响应当成新请求的结果。

中断不能撤回已经发给设备的控制命令，也不等于设备已经停止。应根据实际阶段标记“已取消”或“结果未知”。对于无法可靠区分新旧响应的协议，不能声称可以无条件立即发送并正确匹配，需采用适合该协议的恢复措施。

还要支持按连接暂停、恢复定时任务，方便连续手动测试，避免后台定时写入覆盖刚刚手动设置的值；其他连接可继续运行。软件中断不替代硬件急停。

## 12 典型使用过程

### 已有设备模板

选择模板 → 填写设备连接参数 → 自动带出标签和调用规则 → 单次验证 → 使用标签读写或调用动作 → 需要时加入对应周期的定时组。

### 新称重设备或自定义串口设备

参照协议手册配置连接 → 测试查询和响应 → 用可视化或脚本解析重量、单位、状态 → 生成并命名标签 → 配置写入或动作能力 → 保存为可复用模板。

### 先写再读的周期测试

配置目标值标签及反馈标签 → 绑定“写入、等待、读回、核对”的完整流程 → 加入所需周期组 → 查看逐步结果、超期与失败状态，避免把两步拆成互相抢占串口的任务。

以上是预期使用场景，不是已经完成的设备实测记录。

## 13 已收敛的决定与后续边界

本次已收敛：
- 测试与控制是核心，模板复用和标签调用贯穿全过程。
- 可视化与脚本都要，发送与接收两端都支持。
- 模板规则与设备实例配置分离。
- 标签统一调用，但数据读写与动作的语义必须明确。
- 周期设置自动创建或复用定时组，同组统一周期，拖入服从组周期。
- 支持完整查询事务及真正先写后读的组合流程。
- 手动调用既能排队，也能明确中断；超时、迟到响应和未知结果不能被隐藏。

尚未定案，不作为已承诺实现：
- 具体运行时版本及前端选型仍待定；后续已确认 .NET 实现方向、后台加网页形态及 64 位平台目标，详见 [运行架构与平台兼容需求](运行架构与平台兼容需求.md)。
- Socket 的 TCP、UDP 覆盖方式，具体 PLC 品牌和驱动。
- 脚本语言、权限和隔离机制。
- API、数据持久化范围待定；关闭网页与后台执行的边界以 [运行架构与平台兼容需求](运行架构与平台兼容需求.md) 为准。
- 定时组作用范围、同一调用跨组重复配置的处理，以及具体排程策略。

本文记录需求共识，不替代后续技术方案、实现任务或验收证据。后续只在新增内容讨论确认后继续补充，不把建议、实现状态和验收结论混写。

## 14 运行主机资源监视

状态：本次补充需求已确认；尚未实现、未验收。

在网页的“主机状态”中实时显示**运行弦桥后台的那台主机**的资源使用情况。不管从哪台电脑打开网页，监视对象都是后台运行主机，不是浏览器所在电脑，也不是正在通讯或采集的仪器设备。

显示范围：
- 主机 CPU 使用率和内存占用。
- 各网卡的发送、接收速率。
- 各磁盘容量、剩余空间，以及读写速率。
- 上述资源指标的短时趋势，便于观察近期负载变化。
- 单独列出弦桥自身进程的 CPU 和内存占用，与整台主机的资源指标区分，帮助判断负载是否来自弦桥。

无法获取的指标应明确显示“不支持”或“暂不可用”，不能用数值 0 假装正常采集。具体刷新周期和短时趋势窗口留待方案确定；本项确认网页展示入口，不据此指定整体技术栈或支持平台。

本项只做监视，不包含清理磁盘、结束进程、修改系统设置，也不增加告警、长期历史存储或自动运维功能。
