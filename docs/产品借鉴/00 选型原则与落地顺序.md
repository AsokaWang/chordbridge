# 弦桥 GitHub 借鉴的选型原则与落地顺序

研究日期：2026-10-24。本文是研究后的选型方法与验证建议，不表示已经完成程序实现、依赖集成、设备测试或平台认证。

## 1 已确定的方向

程序以 .NET 编写，采用后台运行与浏览器操作的形态，面向 64 位 Windows、Linux 与 x64、ARM64 目标组合。业务依据是 [想法清单](../01%20想法清单.md) 和 [运行架构与平台兼容需求](../运行架构与平台兼容需求.md)。

研究不能改变以下共识：标签统一调用；数据标签与动作语义区分；同周期自动组，拖入采用组周期；完整串口事务不被普通任务交错；读取与真实控制分开处理；可视化和脚本均支持收发；模板与实例分离；只监视主机资源，不进行自动运维。

## 2 三种借鉴方式分别处理

| 方式 | 使用前提 | 应交付的依据 |
| --- | --- | --- |
| 引用 .NET 类库 | API、目标框架、许可证、依赖及所需功能适用 | 固定版本、许可证清单、实际编译与协议测试 |
| 借鉴源码设计 | 看懂职责和失败边界，确定代码复制是否合法 | 原始来源、机制说明、自己的契约与回归用例 |
| 借鉴产品架构或布局 | 技术栈可能完全不同，不等于可直接集成 | 对照页面/源码，指出能借鉴和应舍弃的部分 |

仓库公开可读不等于可以无限制复制。MIT、Apache、GPL、LGPL、商业模块以及没有明确许可证的示例必须分别核查。本文中的许可证记录是工程筛选信息，不替代发布前对具体版本及依赖的合规检查。

“成熟”应由文档、测试、版本发布、维护响应和实际适配证据共同支持，不只看 stars、README 协议列表或最近一次提交。未确认的信息明确留空或标待验证，不用猜测补全。

## 3 建议采用的最小架构

推荐优先验证 **模块清楚的单主机 .NET 后台**，而不是先搭建微服务、消息集群或云平台：

1. 协议适配层负责串口、Socket、Modbus 和 OPC 的原始通信与能力声明。
2. 连接执行器统一管理每个连接的完整事务、超时、手动优先级、取消与迟到响应恢复。
3. 模板、标签和调用层负责稳定身份、参数化指令、解析结果、质量、动作及组合流程。
4. 定时层根据统一周期组生成调用，交给连接执行器，不绕过它直接操作串口。
5. 网页操作层与实时状态层展示后台状态，不承担设备轮询，不因浏览器重连重新发送控制。
6. 主机资源监视通过平台适配采集，与设备采集通道区分，无法提供的指标明确标注。

这是建议的职责分层，不是最终项目目录或已选框架。OPC DA 是否使用独立 Windows 桥接进程、脚本是否使用隔离进程，须由兼容性及风险验证决定。

ASP.NET Core 是可评估的 .NET Web 基础，而不是本次已经选定的完整前端方案。微软提供从 BackgroundService 向 SignalR 客户端发送更新的示例，支持“后台工作、网页接收状态”的分工；这些机制本身不替代工业通讯调度和控制防重。[ASP.NET Core 仓库](https://github.com/dotnet/aspnetcore)；[后台服务与 SignalR 官方示例](https://learn.microsoft.com/en-us/aspnet/core/signalr/background-services?view=aspnetcore-10.0)。

## 4 建议的验证顺序

以下是后续获准实施时的验证顺序，本次不运行第三方项目，也不向真实设备发控制指令。

### 第一步 贯通一个可观察的调用链

先用离线样例及模拟设备验证：连接、一次完整查询、响应分帧、重量和单位等多字段解析、标签结果、网页显示。用同一个示例确认查看缓存值不会触发查询，失败不会产生假零值。

### 第二步 验证最容易出错的调度

配置 500 毫秒与 2 秒两组，确认拖入即遵从组周期；模拟设备延迟、超期、断线和迟到响应。验证不会无限堆积，同一串口不会交错，合并只针对等价且无副作用的读取，不把重复写控制合并掉。

### 第三步 验证控制与脚本边界

验证真正先写后读的流程、结果未知、手动排队和中断后恢复。脚本必须有输入输出契约和资源约束；对任意脚本执行的安全性不能只靠“设了超时”。

### 第四步 扩展协议和平台

分别验证 Modbus、OPC UA、OPC DA 等，不以一个驱动成功代表全部成功。Windows x64、Linux x64、Linux ARM64、Windows ARM64 分别检查运行时、串口驱动、原生依赖和所需协议；受限组合列清替代方式。

.NET 官方的系统支持矩阵只说明运行时范围，不能证明特定 USB 串口芯片、OPC DA 组件或硬件监测依赖可用。[.NET 官方系统矩阵示例](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md)。具体 .NET 版本和最低操作系统版本尚未在本次研究中锁定。

### 第五步 再确定完整界面与发布方式

以连接、标签、事务调试、定时组、模板与主机状态为核心页面。选择前端与发布方式时验证长列表、日志持续流入、多个连接、网页断线恢复等场景，不先照搬大型 SCADA 的画布或工业云平台的全部菜单。

## 5 每个候选进入实施前的检查

- 固定仓库与组件版本，记录源码提交和许可证，而不是永远引用滚动的 main/master。
- 明确“已见文档证据”“读过源码”“实际运行验证”三个层次；本轮不宣称最后一层。
- 对每个承诺的平台组合验证，而不是由 .NET Standard 或 AnyCPU 字样推导全部可用。
- 检查依赖和商业功能边界、安装发布体积及更新影响。
- 用弦桥自己的调用、标签、事务和调度契约包裹第三方实现，避免业务模型绑定某一家 SDK。
- 保留原始报文、错误、时间、版本和验证证据，便于更换库后重跑回归。

## 6 本轮不会擅自确定的事项

前端框架、脚本语言、数据库、安装方式、网络暴露与身份权限、确切平台版本、PLC 品牌驱动、OPC DA 桥接协议以及正式性能指标仍需结合验证收敛。不会因为搜到某个仓库就把这些全部写成已确认需求。
