# RS232 串口测试与指令标签借鉴

核查日期：2026-10-24。本文为 GitHub 与官方资料研究，不是代码实现或硬件实测。

.NET 是用户已确认的实现方向；下述具体库和设计仍是候选建议。Windows x64、Linux x64、Linux ARM64、Windows ARM64 必须逐项验证，不能由“.NET Standard”推导出驱动和全部功能已经兼容。

## 结论

建议把串口字节传输、报文分帧、设备指令、标签映射拆开。不要为每台称重仪复制一个串口类，也不要把“一次收到数据事件”当成“一条完整响应”。RS232 是电气接口，不自带“重量”“去皮”等业务标签。[接口层区别](https://www.analog.com/en/resources/technical-articles/guide-to-selecting-and-using-rs232-rs422-and-rs485-serial-data-standards.html)

## 弦桥的落地建议

1. `SerialConnection` 仅保存端口、波特率、校验、停止位、数据位、流控和连接状态；模板不能固定某台主机的 COM 编号。
2. `FrameRule` 负责终止符、固定长度或长度字段。先积累原始字节，再解码；HEX 测试也走同一条通道。
3. `ReadOperation` 包含发送查询、等待完整响应、校验、解析和更新标签。发查询不是给某个“发送标签”写值。
4. 一次响应中重量、单位、稳定状态共用批次和采集时间；缓存当前值与主动读取分开。
5. 接收循环与网页生命周期解耦。定时组和手动操作都进入同一连接队列，组合操作不被插入。
6. 断线重连只恢复连接，不自动重发未知结果的去皮、清零等动作。

Microsoft 明确说明 DataReceived 不保证每个字节都触发，因此它不能作为报文边界。具体读取方案应结合流式 API、缓冲和取消行为验证，而非机械照抄教程。[官方事件语义](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport.datareceived)

## 能复用与不能直接得到的部分

可以复用端口 I/O 和成熟缓冲实现；设备手册、解析字段、标签注册、模板版本、同周期组和执行证据仍需弦桥实现。RJCP 的兼容行为不应当作与 System.IO.Ports 完全等同。选择库前还要核对其本机依赖许可证及打包内容。

## 后续验收证据

- 使用真实 RS232 或 USB 转 RS232 适配器，记录系统、架构、驱动版本和设备型号。
- 将一条响应拆成多次到达，或一次到达两条响应，解析结果仍正确。
- 超时、拔插、端口被占用、关闭时阻塞、迟到响应均能正确区分；失败不生成假零值。
- 同一查询映射多个标签不重复发包，500 ms 组全部按统一周期调度；超期不重叠补跑。
- 模板换设备后只改实例端口参数，不覆盖另一台设备配置。
