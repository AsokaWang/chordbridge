# 完整事务与先写后读组合流程的实现借鉴

核查日期：2026-10-24。本文是基于 GitHub 与官方资料的借鉴研究；“建议”不是已确认的详细设计，也不是已实现或实测结果。用户已选择 .NET 方向，具体版本与依赖尚未锁定。

## 结论

优先用有限步骤的事务执行器满足弦桥当前范围；借鉴 Elsa 的活动组合与可追踪状态，但不因需要“写入后读回”就引入完整业务流程平台。

## 已核查项目

- [Elsa Workflows](https://github.com/elsa-workflows/elsa-core)：C#/.NET，MIT，main，2026-10-24 最近推送，未归档；支持代码、JSON 和可视化定义，以及组合活动。README 也列出设计器限制，不能把所有流程类型等同于已完整支持的图形编辑体验。
- [Node-RED serial request](https://github.com/node-red/node-red-nodes/blob/master/io/serialport/README.md)：请求节点采用 FIFO，等待响应或超时后才处理下一个。该包 [package.json](https://github.com/node-red/node-red-nodes/blob/master/io/serialport/package.json) 标 Apache-2.0、2.0.3；仓库最近推送 2026-10-22。它是 Node.js 实现，只借鉴通讯事务边界，不直接引入 .NET。

## 对应两类用户场景

**查询事务**：生成查询字节 → 发送 → 等待完整响应 → 解析 → 更新关联标签。发送查询不是修改设备参数，因此不需要人为拆成“写标签＋读标签”。

**控制组合**：验证参数 → 发送写入 → 判断协议应答 → 按设备规则等待 → 读取反馈 → 判断是否一致。目标标签与反馈标签可以不同，整组必须保留统一调用 Id 与各步骤 Id。

## 弦桥建议落地

给流程定义限定步骤：查询、写值、动作、等待、条件核对；每步声明副作用和可重试性。对单连接流程取得完整事务占用权，执行完或明确中断前不被普通任务穿插。跨连接流程不能假装为数据库式原子事务；如将来需要，应另做锁顺序和部分成功设计。

运行状态建议区分未开始、执行中、步骤成功、失败、取消、结果未知。写入被设备接收后程序崩溃，不能从“未记录完成”推导“没执行”；自动恢复执行位置更不能默认重发。这是弦桥需要补充的控制语义，不是采用 Elsa 自动得到的保证。

## 不宜照搬

Elsa 的持久工作流、HTTP、消息和长任务能力超出当前简单通讯流程；全套引入会增加部署与权限表面。建议先验证有限步骤状态机，只有后续确有复杂流程管理需求再评估 Elsa 作为流程编辑与执行层。500ms 高频事务不默认每步落业务工作流数据库。

## 后续验证证据

写入成功读回失败能展示部分结果；反馈不匹配不能算成功；去皮动作不会被读取重试重复触发；同串口其他请求在整组完成后才进入；中断后保留已发送阶段；超期不并发再开同流程；断电恢复不自动重放控制。
