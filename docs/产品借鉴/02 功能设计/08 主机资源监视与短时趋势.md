# 主机资源监视与短时趋势的实现借鉴

核查日期：2026-10-24。本文是基于 GitHub 与官方资料的借鉴研究；“建议”不是已确认的详细设计，也不是已实现或实测结果。用户已选择 .NET 方向，具体版本与依赖尚未锁定。

## 结论

优先借鉴操作系统指标采集器，而不是用温度、风扇等硬件传感器库替代主机资源监视。需要监视运行弦桥后台的主机及弦桥进程，不是浏览器机器。

## 已核查项目

- [prometheus-net](https://github.com/prometheus-net/prometheus-net)：MIT，master；GitHub API 最近推送 2024-04-11，未归档。可复用指标模型与 .NET 集成；项目存在不等于当前更新频繁，也不要求弦桥必须部署 Prometheus。
- [prometheus-net.SystemMetrics](https://github.com/Daniel15/prometheus-net.SystemMetrics)：MIT，master，最近推送 2025-08-31，未归档。README 列出 Windows/Linux CPU、内存、网络累计字节及文件系统空间；Linux load average 是另一种指标，不应当作CPU百分比。该项目不是全部磁盘读写速率的一站式实现。
- [.NET runtime](https://github.com/dotnet/runtime)：MIT，可研究 Process、NetworkInterface、DriveInfo 等平台实现；主机CPU与磁盘I/O通常仍需平台采集器，不能只靠当前进程API完成。

## 弦桥建议落地

定义平台无关采样结果：指标 Id、值、单位、采样时间、有效性、范围（主机或进程）、来源。每个平台的采集器独立注册；某一项失败不能让所有指标与设备通讯一起失败。

CPU、网卡、磁盘吞吐由两次计数差与实际时间差计算。首次采样、计数回绕、设备移除或时间差无效时标“暂不可用”，不要产生巨大负值或假0。明确CPU归一化口径，区分单核100%与整机100%；进程内存区分工作集和托管堆，后者不等于进程总内存。

磁盘空间是文件系统/卷视角，吞吐是块设备/物理磁盘视角，挂载点与设备映射需标清。各网卡分别展示，避免虚拟网卡重复汇总造成“总流量”翻倍。容器内采样必须标明容器/宿主机范围，不能默认穿透获得宿主机全部指标。

短时趋势建议有界内存环形缓冲，窗口与采样周期待确定；后台统一采样，不能每打开一个网页就增加采样循环。采样速度不必跟随最短设备轮询周期。

## 平台缺口

Windows/Linux x64、ARM64 均需实际验证；第三方库声明支持系统不等于所有权限、计数器和架构都适用。缺失指标显示“不支持/暂不可用”，不提升权限或修改系统设置。磁盘读写速率需要补充并核查 Windows/Linux 原生指标适配，不能把“可用空间”误写成已支持吞吐。

## 后续验证证据

两台机器远程打开页面时显示相同后台主机；网卡插拔不中断程序；磁盘不可访问有明确状态；趋势窗口恒定内存；主机与进程CPU口径可对照系统工具；无权限不显示0；CPU采样负载不会明显干扰500ms通讯组。无告警、长期存储、清盘或杀进程扩展。
